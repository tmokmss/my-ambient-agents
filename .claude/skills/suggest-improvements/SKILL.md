# Suggest Improvements

レポートの生成・コミット・プッシュが完了した後に、今回の実行を振り返り改善提案を GitHub Issue として起票する。

**大前提**: open Issue は既に数百件ある。新規起票は最後の手段であり、
既存 Issue へのコメント（+1）の方が価値が高い。コメント数は Triage エージェントが
優先度として使うため、既存 Issue に積む方が対応が早まる。

## 手順

### 1. 改善点の洗い出し

今回の実行結果を振り返り、改善できる点を1-3件考える。例:
- データソースの追加・変更・削除（取得失敗が続くソースの代替など）
- レポート構成やフォーマットの改善
- フィルタリングやキーワードの改善
- プロンプトの改善

改善点が特にない場合は Issue を作成せず、このスキルを終了してよい（無理に作らない）。

### 2. 見送り済み台帳の確認（最初に必ず実行）

`docs/declined-issues.md` を読む。改善案が台帳に載っているテーマと同じなら、
**Issue を起票してはならず、コメントもしない**。そのまま次の改善案に移る（または終了する）。

例外: 見送りの前提が明確に崩れた場合のみ起票してよい。
（例: 「外部要因」で見送られたソースが復旧した、代替ソースが新たに使えるようになった）
その場合は本文の冒頭に `関連: #{台帳の Issue 番号}（見送り後に状況が変化）` と、
**何がどう変わったのか**を必ず明記する。

### 3. 既存 Issue の検索

全件リストは巨大なので、**キーワード検索**で絞り込む。改善案のキーワード（データソース名、
現象を表す語など）を2-3パターン変えて検索し、open / closed の両方を確認する:

```bash
gh issue list --state all --limit 30 --search "Boing Boing in:title"
gh issue list --state all --limit 30 --search "スポンサード in:title,body"
```

自分のエージェントのプレフィックスで絞るのも有効:

```bash
gh issue list --state open --limit 1000 --json number,title,comments \
  --jq 'sort_by(-(.comments | length)) | .[] | "\(.number)\t[c=\(.comments | length)]\t\(.title)"' \
  | grep -F "[${AGENT_SLUG}]"
```

**表現が違うだけの同一課題を見落とさないこと。** 検索結果のタイトルを読み、少しでも近いものがあれば
`gh issue view <番号>` で本文を確認する。重複起票は Dedupe エージェントの負荷になる。

### 4a. 類似の **open** Issue がある場合

コメントで +1 する（**新規起票はしない**）:

```bash
gh issue comment {issue番号} --body "本日（{日付}）の {エージェント名} 実行でも同様の課題を確認。{追加の観察があれば記載}"
```

同じ内容を繰り返すだけのコメントは避け、今回固有の観測（件数・URL・失敗した挙動など）を1つは含める。

### 4b. 類似の **closed** Issue がある場合

原則 **何もしない**。close されている＝「対応済み」「重複として集約済み」「対応しないと判断された」
のいずれかであり、同じ提案を繰り返さない。

ラベルを確認して判断する:
- `wontfix` → 見送り済み。**絶対に再起票しない**（台帳 `docs/declined-issues.md` と同じ扱い）
- `duplicate` → 集約先の Issue（close コメントに `#<番号>` が書かれている）を開き、そちらが open なら 4a の手順でコメントする
- ラベルなし（対応済み）→ 下記の例外に該当する場合のみ起票してよい

例外: closed-as-completed（fix がマージ済み）にもかかわらず同じ症状が再発しており、
明らかに修正が不十分・回帰したと判断できる場合 → 新規 Issue を起票し、本文の冒頭で
`関連: #{closed issue 番号}（修正後に再発）` を明記する。

### 4c. 類似の Issue が（open/closed のいずれにも）ない場合

新規 Issue を作成する:

```bash
gh issue create \
  --label "enhancement" \
  --title "[{エージェント名}] {改善内容の要約}" \
  --body "{改善の背景・理由・具体的な変更案}"
```

タイトルは**根本原因**が分かる表現にする（症状の羅列ではなく「何が原因で何が起きるか」）。
同じ根本原因の Issue が別タイトルで乱立するのを防ぐため。
