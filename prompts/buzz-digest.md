現在の日本時間: ${JST_TIME}

世界のバズ・トレンドを収集し、暇つぶしに読めるダイジェストレポートを日本語で生成せよ。

## データソースと取得方法

以下の5ソースからデータを取得する。
注意: WebFetch ツールでブロックされるサイトがあるため、データ取得には curl コマンドを使うこと。
JSON のパースには jq を使うこと。

### 1. はてなブックマーク (日本のホットエントリ)
RSSを取得してパース:
- https://b.hatena.ne.jp/hotentry/general.rss (総合)
各エントリの title, link, description, bookmarkcount を取得。
このフィードは RSS 2.0 ではなく **RSS 1.0 (RDF)** 形式で、デフォルト名前空間 rss (http://purl.org/rss/1.0/) の要素を参照すること。
名前空間を省いた `.//item` は必ず0件になる。また item は channel の子ではなく rdf:RDF 直下にある。
bookmarkcount は名前空間 hatena (http://www.hatena.ne.jp/info/xmlns#) の要素。

```python
import xml.etree.ElementTree as ET
ns = {'rss': 'http://purl.org/rss/1.0/', 'hatena': 'http://www.hatena.ne.jp/info/xmlns#'}
root = ET.parse('hb.rss').getroot()   # ルートは rdf:RDF
items = root.findall('rss:item', ns)  # channel の子ではなく RDF 直下
for it in items:
    title = it.findtext('rss:title', '', ns)
    link  = it.findtext('rss:link', '', ns)
    desc  = it.findtext('rss:description', '', ns)
    bc    = it.findtext('hatena:bookmarkcount', '', ns)
```

正規表現でパースする場合、実タグは `<item rdf:about="...">` なので `<item>` ではなく `<item [^>]*>` にマッチさせること。
パース結果が0件だった場合は「取得失敗」と判断する前に名前空間指定の誤りを疑い、上記の方法で取り直すこと。

候補が揃ったら、ピックアップ前に「重複排除」の「同一レポート内の重複（はてなブックマークの同一事件）」に従い、
はてブ候補の全件を同一の出来事ごとにグループ化すること。

### 3. Google Trends (日本の検索トレンド)
RSSを取得してパース:
- https://trends.google.co.jp/trending/rss?geo=JP
名前空間 ht (https://trends.google.com/trending/rss) の要素を参照すること。
各エントリの title, ht:approx_traffic を取得。
関連ニュースがある場合は ht:news_item 内の ht:news_item_title と ht:news_item_url も取得。
ただし ht:news_item が0件、または ht:news_item_url がすべて空のエントリは候補から除外し、次点のキーワードへ繰り上げる
（トラフィックの多寡にかかわらず除外する）。話題になった根拠となるニュース記事が取れたエントリのみを掲載し、
推測でトレンド入りの理由を書いてはならない。

また geo=JP のフィードでも稀に他地域・他言語のキーワードが混入するため、
(a) キーワードにひらがな・カタカナ・漢字が1文字も含まれず、**かつ** (b) そのエントリの ht:news_item_title がすべて日本語文字（ひらがな・カタカナ・漢字）を含まない
（＝関連ニュースが全件外国語）エントリも候補から除外し、次点のキーワードへ繰り上げる。
日本の検索トレンドとして「なぜ日本で話題なのか」を説明できないためである。
判定は上記 (a)(b) の AND で機械的に行い、**片方だけ該当する場合は除外しない**こと。
たとえば `chelsea` のように英字キーワードでも日本語の関連ニュースが紐付くもの、
`李在明` のように日本語文字を含むキーワードに外国語のニュースが混じるものは、いずれも除外対象ではない。

関連ニュースが日本語の国内記事であっても、`ht:news_item` は Google 側で機械的に紐付けられるため、
キーワードとは**別人・別商品・別事象**を扱う記事が混入することがある。
そこで（空・全件外国語の除外を終えた候補について、後述の対戦カード形式の低優先化より**前**に）
各候補の `ht:news_item` を**全件**確認し、「そのニュースがキーワード自体の話題を説明しているか」で関連性を判定すること。

- キーワード文字列が `ht:news_item_title` に含まれていれば「関連あり」と判断してよい（十分条件）。
- 含まれない場合のみ記事の内容で判断する。**単純な文字列含有チェックで「関連なし」と決めてはならない。**
  キーワード `黒柳 徹子`（空白入り）に対しニュースのタイトルが `黒柳徹子`（空白なし）で文字列一致しない例や、
  キーワード `ボクシング` に対しニュースが具体的な選手名だけでキーワード語を含まないが同じ試合を説明している例があるため、
  含有チェックは**「関連あり」を確定させる用途にのみ**使う。
- 芸能・スポーツといった大カテゴリが一致していても、別人・別商品・別事象を扱う記事は「関連なし」とする。
  例:「シソンヌ」に対する「あのちゃん」の記事、「宝くじ ロト7」に対する「ロト6」の記事、
  「島袋将」に対する「大坂なおみ」の記事、「セントマーガレット病院」に対する「千葉大病院」の記事。

判定結果の扱いは次のとおり:

- 一部の `ht:news_item` だけが関連する場合は、**関連する item を解説文とリンクに採用する**（1件目を機械的に採用しない）。
- `ht:news_item` が全件無関係な場合は「関連ニュース情報が空」と同じ扱いで候補から除外し、次点のキーワードへ繰り上げる。
  無関係なニュースをリンクしたり、推測でトレンド入りの理由を書いたりしてはならない。
  Web 検索などで関連ニュースを探し直す必要はない。

さらに、キーワードが「阪神 対 巨人」「csk vs kkr」「coritiba x corinthians」「A×B」のように
チーム名・選手名が2つ並ぶ**対戦カード形式**になっている場合は、**低優先**の候補として扱う。
日本語表記・ローマ字/外国語表記の双方を対象とし、競技・リーグは問わない（NPB / MLB / J リーグ / NBA / IPL / 海外サッカーなど一律に扱う）。
これらは試合日程や途中経過を調べる検索が瞬間的に集まったものであり、「その日の話題」としての読み物価値が低いうえ、
**別々の試合**のカードが同時に複数ランクインしてセクションの枠を占有することが恒常的に発生するためである
（同じ試合に由来する複数キーワードは後述の「同一イベント」の集約で処理されるが、異なる試合同士はそれでは減らせない）。
判定は `ht:approx_traffic` の多寡によらず行う。「1000+」のような小さいボリュームでも試合日程検索由来であれば低優先の対象になりうる。

ただしこれは**ハード除外ではなく低優先化**であり、次の順序で適用すること:

- 対戦カード形式**以外**の候補だけで所定の件数（3件以上）を満たせる場合に限り、対戦カード形式のキーワードをスキップして次点を繰り上げる
- 対戦カード形式以外の候補が所定の件数に満たない場合は、対戦カード形式のキーワードも通常どおり採用して件数を満たす。
  このルールが原因で掲載件数が3件未満になったり、「※ …により N 件のみだった」の注記が必要になったりしてはならない
- 例外として、リーグ優勝決定戦・チャンピオンシップの決勝・国際大会（W杯・五輪・WBC など）の試合のように、
  関連ニュースからその競技のファン以外にも波及する重要度が高いと判断できるものは、低優先扱いにせず通常どおり採用してよい

これらの除外を終えたら、ピックアップ前に「重複排除」の「同一レポート内の重複（Google Trends の同一イベント）」に従い、
残った候補を同一の出来事ごとにグループ化すること。

### 4. YouTube Trending (トレンド動画)
YouTube Data API を使用して、US と JP の2地域のトレンド動画を取得する。
50件×2リージョンの生 JSON をそのままコンテキストに載せるとトークンを浪費するため、
必ず以下のように jq で必要なフィールドだけに射影してから読むこと:

```bash
# US（JP は regionCode=JP に変えるだけ、他は同一）
curl -s "https://www.googleapis.com/youtube/v3/videos?part=snippet,statistics&chart=mostPopular&regionCode=US&maxResults=50&key=$YOUTUBE_DATA_API_KEY" \
  | jq -r '.items[] | select((.statistics.viewCount // "0" | tonumber) >= 10000) | [.id, .snippet.title, .snippet.channelTitle, .statistics.viewCount] | @tsv'
```

出力は `video ID<TAB>タイトル<TAB>チャンネル名<TAB>再生数` の TSV になる。description や thumbnails は使わないので射影で落とすこと。
この jq の `select` が「`statistics.viewCount` が 10000 未満（ライブ配信中・終了直後など視聴数未集計の動画）を除外する」処理を兼ねている。
viewCount が非公開の動画では `.statistics.viewCount` が null になり `tonumber` がエラーになるため、`// "0"` のガードを外してはならない。
各動画のURLは https://www.youtube.com/watch?v={id} の形式でリンクすること。
`maxResults` を API の上限である 50 にしているのは、本エージェントが1日3回実行され、重複排除が直近3日分（最大9レポート）のレポートを参照するため、
上位20件では過去レポートと重複しない候補が枯渇するからである。`chart=mostPopular` の quota コストは取得件数によらず 1 unit なので、50件取得しても消費は増えない。
候補はレスポンスの並び順（＝トレンド上位順）に上から見ていき、未既出のものを再生数の多い順に採用する。上位の話題性を優先する方針は変えず、あくまで候補プールを広げるだけである。
注意: API キーは環境変数 $YOUTUBE_DATA_API_KEY を直接参照すること。キーの値を echo や print で出力してはならない。
US と JP の両方を取得したら、ピックアップ前に「重複排除」の「同一レポート内の重複（YouTube US / JP）」に従い、両リージョンに共通して出現する video ID をチェックすること。

### 5. 英語圏ネットカルチャー (Boing Boing + Atlas Obscura)
以下の2つのRSSを両方取得してパースする。どちらも RSS 2.0 で item/title・link・description の構造が同じなので、同じパース処理を流用してよい:
- Boing Boing: `curl -sL --max-time 30 -A "Mozilla/5.0 (compatible; ambient-agent/1.0)" "https://boingboing.net/feed"` (約30件)
- Atlas Obscura: `curl -sL --max-time 30 -A "Mozilla/5.0 (compatible; ambient-agent/1.0)" "https://www.atlasobscura.com/feeds/latest"` (約27件)
各エントリの title, link, description, category（複数あり得る）, dc:creator を取得し、どちらのフィード由来かを保持しておく（レポートでソース名を併記するため）。

`description` は両フィードとも **HTML 断片**（`<img>` や `<p>` を含む）なので、必ずタグを除去してからテキストとして扱うこと。
どちらのフィードも RSS 2.0 の `./channel/item` なので、同じスクリプトで URL だけ差し替えてパースできる:

```bash
curl -sL --max-time 30 -A "Mozilla/5.0 (compatible; ambient-agent/1.0)" "https://boingboing.net/feed" | python3 -c "
import sys, re, html, xml.etree.ElementTree as ET
ns = {'dc': 'http://purl.org/dc/elements/1.1/'}
def clean(s):
    s = re.sub(r'<[^>]+>', ' ', s or '')
    return re.sub(r'\s+', ' ', html.unescape(s)).strip()
for it in ET.fromstring(sys.stdin.read()).findall('./channel/item'):
    cats = '/'.join(c.text or '' for c in it.findall('category'))
    print('TITLE:', clean(it.findtext('title', '')))
    print('URL:', it.findtext('link', ''))
    print('CATEGORY:', cats); print('CREATOR:', it.findtext('dc:creator', '', ns))
    print('DESC:', clean(it.findtext('description', ''))[:600]); print('---')
"
```

タグ除去の前提について、以下を守ること:

- Boing Boing の `description` は**先頭が `srcset` 付きの巨大な `<img>` タグ**で1000文字前後埋まっており、
  raw の先頭だけを見ると「HTML タグしか無く本文が無い」ように見える。**先頭を見て本文の有無を判断してはならない。**
  上記の `clean()` を通すと `<img>` の後ろに続く `<p>` の本文プレビューが現れ、1記事あたり **350〜600文字程度**のテキストが得られる（全件で得られる）。
- 解説文はこのタグ除去後の本文プレビューを根拠に書くこと。タイトルからの推測で内容を書いてはならない。
- 末尾の `— Read the rest` / `The post … appeared first on Boing Boing.` は全記事共通の定型句なので、解説の材料にしない。
- Boing Boing のフィードに `<content:encoded>` は**存在しない**ので参照しない（全件不在）。
- 個別記事ページを curl / WebFetch して概要を取り直すフォールバックは**行わない**。
  上記のとおり `description` だけで十分な本文プレビューが得られるうえ、boingboing.net は Bot 判定のチャレンジページを返すことがあり時間を浪費するため。
- Atlas Obscura の `description` も同じ `clean()` を通すこと。raw は最大 13KB 超あり、タグ除去でコンテキストも節約できる。

Boing Boing のエントリのうち、`<category>` に `BoingBoing Shop` または `shop` を含むもの、
あるいは `<dc:creator>` が `Boing Boing's Shop` であるものは、アフィリエイト目的の商品販売・オンラインコース紹介記事
（スポンサードコンテンツ）であるため、ピックアップ候補から必ず除外する。
「$19.99 のこのアプリが…」のようにタイトルだけではニュース記事と区別がつかないため、
タイトルの文面ではなく必ず category / dc:creator フィールドで機械的に判定すること。
この除外は Boing Boing にのみ適用し、Atlas Obscura には適用しない。

片方のフィードだけ取得に失敗した場合は「取得失敗時の対応」のルールに従いリトライせずスキップし、取得できた側だけでこのセクションを成立させる。

## 取得失敗時の対応

各ソースの取得が失敗した場合（HTTP エラー、空レスポンス、パース不能など）は、リトライせずそのソースをスキップしてレポートに「取得失敗」と明記する。
最低2ソース以上のデータが取得できればレポートを生成する。全ソース失敗の場合はレポートを生成しない。

## 重複排除

### 過去レポートとの重複

以下のコマンドを実行し、過去レポートに掲載済みのタイトル・URL 一覧を取得する:

```bash
node scripts/report-index.mjs ${AGENT_SLUG} 3 > /tmp/past-index.tsv
```

- **このコマンドは他のコマンド（フィード取得の curl 等）と同じ Bash 呼び出しにまとめず、単独で実行すること。**
- 出力は 30KB を超えることがあり、標準出力にそのまま流すと Bash の出力上限に達して先頭 2KB のプレビューに切り詰められる（persisted-output truncation）。上記のように必ず `/tmp/past-index.tsv` へリダイレクトすること。
- リダイレクト後、**中身は Read ツールで `/tmp/past-index.tsv` を直接読む**。`cat` でファイル全体を標準出力に出し直すと同じ truncation が起きる（個別 URL の有無を確かめる `grep` は出力が小さいので構わないが、類似トピックの判定には全件が必要なので Read で全体を読むこと）。
- Read が上限に達して途中までしか読めなかった場合は `offset` を指定して残りを読み切り、**全エントリを必ず参照すること**（コマンドの stderr に出る `entries=N` が総件数なので、読めた行数と突き合わせる）。

本日を含む直近3つの日付ディレクトリ（YYYY-MM-DD）の "${AGENT_SLUG}" レポートから、掲載済み項目を `URL<TAB>タイトル` 形式で抽出したものがファイルに書き出される
（リンクを持たない Google Trends のキーワードは URL 欄が `-` になる）。1日複数回実行時に直近3件がすべて当日分となり前日以前が参照されなくなるのを避けるため、件数ではなく日数で範囲を取っている。
**`src/content/reports/` 配下のレポート本文（.md）を Read や cat で読み込んではならない。** 重複判定に必要なのはタイトルと URL だけであり、Read してよいのは上記の `/tmp/past-index.tsv` だけである。
過去に取り上げたネタと同一または非常に類似したトピックは除外すること。
同じURL、同じ話題の別記事、同一事件の続報、同一YouTube video IDなどは重複とみなす。

### 同一レポート内の重複（はてなブックマーク / Togetter）

はてなブックマークと Togetter の取得結果を **`togetter.com/li/{数値ID}` の ID で突き合わせ**、両方に含まれる URL を検出する。
はてブのホットエントリには togetter.com の URL がそのまま入るため、同じまとめが両フィードに並ぶことは定期的に発生する。
両フィードに出現した URL は **`## Togetter` にのみ掲載し、`## はてなブックマーク` の候補からは機械的に除外する**。
はてブ RSS は40件前後、Togetter hot は10件前後と候補プールの規模が非対称であり、
Togetter 側を優先しないと Togetter セクションの候補が枯渇するためである。
はてなブックマークセクションは除外後の残り候補から次点を繰り上げて所定の件数を満たすこと。
情報を落とさないため、Togetter 側の解説文の末尾に「はてなブックマークでも {users} users を集めている」旨を1文添える
（users ははてブ RSS 側の `hatena:bookmarkcount` から取得する）。
除外の結果 Togetter の候補が3件未満になった場合は、無理に件数を埋めず取得できた件数のみを掲載し、
セクション末尾に「※ はてなブックマークとの重複を除いた新規まとめが N 件のみだった」旨の注記を1行入れる。
Togetter RSS 側に同じ URL が無く、はてブ RSS にのみ togetter.com の URL が出現した場合はクロス重複ではないため、
そのままはてなブックマークセクションで扱ってよい。

### 同一レポート内の重複（はてなブックマークの同一事件）

はてなブックマークのホットエントリには同じ出来事に起因する複数の記事が同時にランクインすることが恒常的にある
（例: 1つの政治スキャンダルに対し複数媒体の速報・続報・解説がそれぞれ別エントリとして立つ、
1人の著名人の訃報を4媒体が同時に報じる）。
そのまま上位から採用するとセクションの大半が同じ話題で埋まり、他ジャンルの話題が押し出されるため、
ピックアップ前にはてブ候補の全件を
「同一の出来事（同じ事件・同じ人物の同一ニュース・同じ訃報・同じ訴訟や発表）に起因するか」でグループ化する。
なお前節の Togetter とのクロス重複による除外を先に適用し、残った候補に対してグループ化を行うこと。
判定材料は以下の2つで、いずれかに該当すれば同一グループとみなす:

- (a) 2つのエントリの title・description が同じ出来事を指している（別媒体が同じ事件を報じた場合を含む）
- (b) タイトルが一致しなくても表記ゆれ・金額や時点の違い・速報と続報の関係にある

**単に同じ人名・組織名を含むだけでは同一グループにしてはならない。**
同一人物の別件ニュース（例: 同じ政治家の外交日程の記事と献金問題の記事）は別の出来事であり、別グループとして扱う。

**同一グループから掲載するのは最大1件**とし、ブックマーク数（`hatena:bookmarkcount`）が最大のエントリを代表として採用する。
同一グループの残りのエントリは候補から機械的に除外し、次点のエントリを繰り上げて所定の件数（3〜5件）を満たす。
はてブ RSS は40件前後の候補プールがあるため、除外しても次点の繰り上げで件数は通常満たせる。
情報を落とさないため、代表エントリの解説文の末尾に
「関連記事: {媒体名}（{users}users）ほか N 件も同じ〇〇を報じている」旨を1文添える
（同一グループの残りが1件だけの場合は「ほか N 件」を省いてよい）。
特定の人物名・事件ワード（「高市」「誹謗中傷」など）を条件にするのではなく、
政治・芸能・訃報・事故・スポーツ・国際ニュースなどあらゆるジャンルに一律にこのグループ化を適用すること。
除外の結果はてなブックマークの候補が3件未満になった場合は、無理に件数を埋めず取得できた件数のみを掲載し、
セクション末尾に「※ Togetter・過去レポートとの重複および同一事件への集約により N 件のみだった」旨の注記を1行入れる。
該当理由が複数あっても注記は2行に分けず、上記のように1行にまとめること。

### 同一レポート内の重複（Google Trends の同一イベント）

Google Trends には同じ出来事に起因する複数のキーワードが同時にランクインすることが恒常的にある
（例: 1つのサッカーの試合に対し、出場選手名・チーム名・対戦カードがそれぞれ別キーワードとして立つ）。
そのまま上位から採用するとセクションの大半が同じ話題で埋まるため、ピックアップ前に全キーワードを
「同一の出来事（同じ試合・同じ事件・同じ作品・同じ人物の同一ニュース）に起因するか」でグループ化する。
判定材料は以下の2つで、いずれかに該当すれば同一グループとみなす:

- (a) 2つのキーワードの `ht:news_item_url` が1つ以上一致する
- (b) URL が一致しなくても `ht:news_item_title` が同じ出来事を指している
  （日本語/英語/現地語の表記違い、表記ゆれ、試合名と出場選手名、イベント名と会場名を含む）

例:「レアル・マドリード」と `real madrid vs real sociedad` は同一試合、「藤ノ川」と「藤の川」は表記ゆれ、
同一の地震に対する「余震」と「首都直下地震」は同一事件であり、それぞれ1グループとして扱う。

**同一グループから掲載するのは最大1件**とし、検索ボリューム（`ht:approx_traffic`）が最大のキーワードを代表として採用する。
同一グループの残りのキーワードは候補から機械的に除外し、次点のキーワードを繰り上げて所定の件数を満たす。
情報を落とさないため、代表キーワードの解説文の末尾に「関連キーワード: A / B（いずれも同じ〇〇に起因）」旨を1文添える。
特定のイベント名（W杯・五輪など）を条件にするのではなく、あらゆるトレンドに対してこのグループ化を適用すること。

### 同一レポート内の重複（YouTube US / JP）

US と JP の `mostPopular` 取得結果を **video ID で突き合わせ**、両方に含まれる ID を検出する。
K-POP の新曲 M/V など世界同時公開の動画では両リージョンに同じ動画が入ることが定期的に発生する。
`statistics.viewCount` は地域別ではなく全世界の累計再生数であり US / JP で同じ値になるため、再生数では掲載先の優劣を判定できない。
両リージョンに出現した動画は **`## YouTube Trending (US)` にのみ掲載し、`## YouTube Trending (JP)` の候補からは機械的に除外する**。
JP セクションは除外後の残り候補から次点を繰り上げて所定の件数を満たすこと。
情報を落とさないため、US 側の解説文の末尾に「JP のトレンドにも同時ランクインしている」旨を1文添える。
除外の結果 JP の候補が3件未満になった場合は、無理に件数を埋めず取得できた件数のみを掲載し、
セクション末尾に「※ US トレンドとの重複を除いた新規動画が N 件のみだった」旨の注記を1行入れる。

## レポート形式

output-report skill に従い src/content/reports/ にファイルを作成する。
- category: "${AGENT_CATEGORY}"
- title: "世界バズ・ダイジェスト（{日本時間の日付}）" の形式にする（例: 世界バズ・ダイジェスト（2026年3月6日））
- slug: ${AGENT_SLUG} (例: src/content/reports/2026-03-06/08-00-${AGENT_SLUG}.md)
- tags: 記事の内容に応じて自由にタグをつける（例: "ai", "gaming", "politics", "security", "culture" など）。ソース名をタグにする必要はない

本文の構造:

ソース別にセクションを分け、各ソースから面白い・注目すべきトピックを3-5件ピックアップする。
単なるタイトル列挙ではなく、なぜ面白いのか・何が話題なのかを1-2文で解説する。
