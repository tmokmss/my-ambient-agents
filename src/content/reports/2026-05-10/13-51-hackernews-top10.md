## 1. [Space Cadet Pinball on Linux](https://brennan.io/2026/05/09/pinball-and-escrow/)

**Score:** 107 | **Comments:** 32 | [Post](https://news.ycombinator.com/item?id=48082968)

Stephen Brennan が Linux 上で懐かしの Space Cadet Pinball を動かす方法を解説。Flatpak を使えば Windows 版のゲームリソース込みで簡単にインストールでき、Full Tilt! Pinball のデータを使えば 1024×768 の高解像度グラフィックも利用可能だ。記事末尾では、販売終了後にソフトウェアが自動的に FOSS ライセンスに移行する「ソースコードエスクロー」の概念についても考察している。

### Key Discussion Points

- **diegomacario**: Shopify が BFCM（ブラックフライデー）のライブ可視化として Space Cadet にインスパイアされたピンボールゲームを制作したと紹介。エンジニア2名＋アーティスト1名で約1.5ヶ月かけて開発した。
- **andai**: GitHub に多数のプラットフォーム（Switch 含む）への移植版やブラウザ版が存在すると共有。Space Cadet はもともと Maxis の Full Tilt! Pinball の一部だったと補足。Windows 95 に DOOM を同梱する案もあったが「ピンボールで十分」と却下された経緯も紹介。
- **flossly**: 記事末尾の「ソースコードFLOSSエスクロー」構想に着目。販売終了時にオープンソース化されるモデルは KDE Free Qt Foundation の仕組みに似ており、ユーザーのベンダーロックイン懸念を軽減できると評価。
- **unleaded**: Full Tilt 版にはマルチボール機能があり Windows 版にはない点を補足。Visual Pinball のより豊富なテーブルも勧めつつ、Space Cadet のゲーム状態がランプの点灯状態に直接連動している実装の問題点（ランクアップ演出中にボールを落とすとランクをスキップできるバグ）を解説。
- **TheAceOfHearts**: 熟練プレイヤーが実際にチルトキーを使うのか疑問を呈し、リスクに見合うほどボールをずらせないのではと述べた。

## 2. [I returned to AWS, and was reminded why I left](http://fourlightyears.blogspot.com/2026/05/i-returned-to-aws-and-was-reminded-hard.html)

**Score:** 138 | **Comments:** 79 | [Post](https://news.ycombinator.com/item?id=48073201)

メルボルン初の AWS イベントを主催した元 AWS 伝道師の Andrew Stuart が、15年間支持してきた AWS への幻滅を詳述。エグレス料金（9セント/GB）・DynamoDB の複雑さ・Lambda のベンダーロックイン・OSS プロジェクトの"横取り"など多数の不満を列挙したうえ、Bedrock で Claude をテストしようとアカウントを再開したところ不審なセキュリティ侵害として凍結され、仕事用メールも4日間使えなくなったと報告した。

### Key Discussion Points

- **aljgz**: AWS の UI には同一画面にスペックと価格が表示されず、2つのテーブルを突き合わせる必要があると指摘。DigitalOcean に移行したところ製品を1ヶ月前倒しでリリースできた経験を語った。
- **tedivm**: 著者の OSS 批判を一部訂正。OpenSearch・Valkey は AWS がライセンス変更を強いたのではなく、上流プロジェクトがライセンスを変更した後に AWS がフォークしたものであり、因果関係が逆だと指摘した。
- **djyde**: Vercel → Hetzner＋Coolify → Cloudflare Workers＋D1＋KV という移行遍歴を共有。Cloudflare は環境変数管理が不要でローカル開発体験が優れ、価格も合理的だと評価。
- **djinn**: AWS は 2023 年以降、大規模レイオフと PIP（業績改善計画）2サイクルにより技術スタッフが著しく減少し、今は自己責任で使うしかないとコメント。
- **jfengel**: 個人プロジェクトで AWS に触れるたびに「明日 VC 資金で無限にスケールアップするための設定」を求められているような感覚に陥ると述べ、Netlify のような抽象化レイヤーに頼っていると説明。

## 3. [Idempotency Is Easy Until the Second Request Is Different](https://blog.dochia.dev/blog/idempotency/)

**Score:** 150 | **Comments:** 69 | [Post](https://news.ycombinator.com/item?id=48047930)

同一の冪等性キーで異なるリクエストボディが送られてきたとき、API はどう振る舞うべきかを掘り下げた技術記事。分散ロック・複合キー（クライアント提供キー＋ペイロードハッシュ）・PENDING 状態の管理など、冪等性実装が想像以上に複雑であることを実例とともに論じている。

### Key Discussion Points

- **xlii**: API はコントラクトであり、クライアントの意図を推測するのではなく冪等性キーの定義に厳密に従うべきだと主張。
  - **mainde**: 現実にはクライアント側バグの修正が数週間かかる場合、バックエンドで数時間かけて対処する方が合理的だと反論。ユーザーを数週間苦しめてまで「正しさ」を守ることはできないと述べた。
  - **pvillano**: クライアントが完璧であることを期待するより、自分が API をフールプルーフにする方を選ぶと表明。
- **mmillin**: 本番環境でこの記事が挙げる問題をほぼ全て経験しており、チームに共有すると宣言。Antithesis の「Definite vs Indefinite エラー」分類をリプレイ挙動の設計に活用することも勧めた。
- **randallsquared**: 「第二リクエストが異なるなら冪等性は適用されない」とシンプルに主張。
  - **zarzavat**: ではリクエストが異なると何でわかるのか？全リクエストをハッシュするのはリソースの無駄。キーを信頼するしかないと反論。
- **DarenWatson**: チェックアウトフローでの実際のサイレントデータ破損事例を詳述。同一キーに異なるペイロードが来た場合は 409 Conflict を返すべきであり、冪等性キーは複合キー（Client_Key＋Hash(Payload)）として扱うべきと提案。分散ロックを使った安全な5ステップの実装手順を紹介した。
  - **spockz**: 分散 KV ストアで冪等性キーだけをロックする方式は、任意のシステムを冪等にするより実装が容易だと同意。
  - **gib444**: 冪等性キーは「信頼できないヒント」として扱うべきだと指摘。フロントエンドとバックエンドがチームとして分断されることで、重要な決定に適切な意見が反映されない問題も提起した。

## 5. [Bun's experimental Rust rewrite hits 99.8% test compatibility on Linux x64 glibc](https://twitter.com/jarredsumner/status/2053047748191232310)

**Score:** 620 | **Comments:** 597 | [Post](https://news.ycombinator.com/item?id=48073680)

JavaScript ランタイム Bun の作者 Jarred Sumner が、Zig で書かれた既存コードベース（約96万行）を Rust へ書き直す実験的なブランチが Linux x64 glibc で既存テストの 99.8% をパスしたと発表。AI（Claude/Mythos）を活用し約6日間で達成した。動機はメモリリークとクラッシュへの疲弊であり、Rust のライフタイム管理と `unsafe` の可視性によって安全性を高めることを目指している。

### Key Discussion Points

- **legerdemain**: 4日前に Jarred 自身が「コンパイルエラー16,000件・バージョン番号すら表示できない」と投稿していたことを引用し、急速な進展に驚きを示した。
  - **Jarred**（本人）: 当時はそれほど早く動作するとは予想していなかったし、パフォーマンスがここまで競争力を持つとも思っていなかったと回答。ブログ記事で詳細を公開予定。
  - **logicprog**: 保守性・パフォーマンス・テストスイートを確認して決断したということだとコメント。
- **mohsen1**: TypeScript の Rust 移植（tsz.dev）を5ヶ月かけて進めており 99.6% のパス率に到達。Rust の厳格な型システムが LLM によるコード生成と相性が良いと強調。一方で設計のビジョンとトレードオフ判断は引き続き人間が担う必要があると指摘した。
  - **cornholio**: Rust は「リファクタリング雪崩」が起きやすく、LLM が段階的にコードを増やすと可読性・保守性が失われる懸念を表明。コンパイルは通るが人間が読めないコードになるリスクがあると警告。
  - **kayson**: Microsoft が TypeScript を Go で書き直した際に Rust を避けた理由（GC などパラダイムの近さ）を引用し、実際に Rust で行ってみての感想を尋ねた。
- **Tiberium**: Zig の unsafe 操作によるクラッシュ・メモリバグが多かった Bun にとって Rust への移行は望ましい変化と評価。ただし unsafe が多用されれば Rust の保証は失われると付言。
  - **lionkor**: `unsafe` だらけのコードでは Rust の安全性保証はほぼ得られず、本番環境での利用は勧められないと警告。
  - **mi_lk**: Bun のクラッシュ率のデータを求めつつ、問題の一因はコード品質であり言語だけの問題ではないと指摘。
- **aurareturn**: 6日間でこの成果を出せることは、今後「計算資源の量」が競争力を左右することを示していると分析。
  - **Aurornis**: テストスイート付きコードベースの言語移植は LLM が得意なタスクの典型であり、すでに実装と目標が揃っているのでゴールへの収束が容易だと解説。
  - **kzrdude**: 「ソフトウェア開発における生産手段の所有が集中する新時代」と皮肉交じりにコメント。
- **jwpapi**: Bun に対する信頼を失っており、Anthropic/Claude に過度に依存しているプロジェクトに見えると否定的。
  - **woah**: 自分のリポジトリでコードを書いている開発者と、HN でそれに文句を言うコメンターのどちらが「駄々っ子」なのかと反論。
  - **Validark**: 個人的には Zig 支持だが、Bun のバッファオーバーランとセグフォルトの多さを考えれば Rust の方が技術的に正しい選択だと述べた。

  - **tux3**: 偽造は国家への攻撃に類する重大犯罪であり、Secret Service はもともと偽造対策のために創設された機関だと解説。この事件はその中でも最小規模の犯罪という異例さがあると補足。

- **Barbing**: 裁判でも同情を集めた判決（1年1日・仮釈放4ヶ月・罰金1ドル）を引用。その後 Juettner は映画化で偽造収入を上回る額を稼いだという「続き」を a_t48 が追記。
